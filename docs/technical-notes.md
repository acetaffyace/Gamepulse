# GamePulse 技术说明与数据口径

[返回项目首页](../README.md) · [数据层设计](v3-data-layer.md) · [开发日志](v3-log.md)

用公开数据做的游戏长线运营看板：Steam 评测与在线、B 站与 YouTube 官方视频。
当前跟踪《鸣潮》《绝区零》《异环》的 Steam 版本与官方视频；
另接入《永劫无间》端游国服官网公告、官方视频样本与 Steam 平台对照，见 [面试采集说明](naraka-interview.md)。

---

## 架构

```
config/*.yml（人工维护）      collectors/*.py（本机白天运行）
游戏 / 版本 / 视频登记 / 指标目录   Steam / 构建号 / B 站 / YouTube / SteamDB 收件箱
            │                              │
            └──────────────┬───────────────┘
                           ▼
            data/gamepulse.sqlite（本机唯一数据源，不进 git）
                           │  python -m store.build
                           │  同步配置 → 派生事件与质量提示 → 校验指标目录与数据 → 导出
                           ▼
            dist/（发布包）
              index.html · app.css · lib/ · pages/ · vendor/
              data/gamepulse.<哈希>.sqlite.gz · data/manifest.json
                           │  python tools/publish_pages.py --push
                           ▼
            gh-pages 分支 → GitHub Pages
                           │
                           ▼
            浏览器：sql.js 打开数据库 → 指标目录 + 查询生成器 → ECharts
```

- **人工维护的在 YAML，机器采集的在 SQLite。** YAML 用 git 管理、方便审阅改动；采集结果进数据库。
- **每个指标只定义一次。** 计算方式写在 SQL 视图（`store/views.sql`）和指标目录（`config/metrics.yml`）里。
  看板页面和自助查询都通过查询生成器（`web/lib/query.js`）用"指标 + 维度 + 筛选"生成 SQL，
  所以同一个数字在任何地方看都一样。
- **发布包是纯静态文件。** 不需要服务器；网页先读 `manifest.json`，再按里面带内容哈希的文件名下载数据库，
  不会读到"新目录 + 旧数据库"的混合状态。
- **数据不进 main 分支。** `gh-pages` 每次发布都是一个没有父提交的新提交，只保留最新一份。

## 这个看板回答什么

| 问题 | 在哪里看 |
|---|---|
| 最近一段时间评测、口碑、在线怎么样 | 运营总览：一行指标卡共用同一个时间范围和截止日 |
| 这个版本比上个版本同阶段表现如何 | 版本对比：A/B快捷或最多6个游戏/版本对象，按Steam开放日D0对齐，截到共同天数；可切换真实日历轴 |
| 一次更新前后的公开信号有什么变化 | 版本对比 → 更新前后7天：前后覆盖完整且窗口内没有其他更新时才计算变化；比率用合计分子/合计分母 |
| 版本更新间隔如何变化 | 版本对比 → 版本节奏：已开放版本的相邻开放日期间隔，按游戏查看最近6个或全部 |
| 官方视频在各语区的传播 | 视频传播：按频道语区分开；发布后同龄对比；同一内容的各语区并排 |
| 写评测的是什么人 | 玩家结构：写评测时的游戏时长、评测语种、评测后是否还在玩 |
| 任意组合 | 自助查询：选指标 × 维度 × 筛选；也可以直接写只读 SQL |
| 数据可不可信 | 数据来源：每个来源的最近尝试、有效数据截至日期、质量提示 |

贯穿始终的原则：**时间上相邻不等于因果。** 事件只标记时间，图表不推断原因。

### 浏览器图形与比较窗口

- 页面采用浅色留白布局，黄、青、粉用于导航、关键指标卡与图表标题的模块标识；深色模式使用对应的低亮度底色。
  总览与快捷版本对比的评测数为黄、好评率为粉、在线与时长为青；其余模块按页面指定的颜色或页面主题取色。游戏、语区等图形系列仍按对象稳定配色，
  来源状态继续使用独立的状态点与文字说明。手机图表采用单列，导航与筛选更紧凑，动效尊重系统的减少动态效果设置。
- 指标卡固定两行，仅展示短标签、主数字、单位与可选趋势；样本、覆盖和缩放解释在“口径”“覆盖”中查看，导出仍包含完整上下文。
  双版本卡片展示B值与相对A的变化，“对照”提供两版原值；覆盖不足时不显示变化。布局与组件变量见 [界面规范](interface-design.md)。
- 页面导入和引擎加载有错误恢复，旧异步渲染不能覆盖新页。数据库与查询/图表引擎并行加载；来源页和SQL模式跳过ECharts。
  单游戏上下文跨页继承，各页日期/阶段独立记忆；没有明确范围时沿用目标页已有选择，不直接混用日历天数与D0阶段。
  主题与导航保留SQL草稿、最后结果、展开、图例、表格搜索排序与页码。失败查询保留上次结果，不自动执行未运行草稿。
- 自助查询的自然周轴以7天步长补齐，只将遗漏周留空；逐日轴仍按天补齐。
- 超过8个图形系列时，只有允许合并的计数/占比类别可以进入“其他”；目录要求独立拆分的
  视频、语区不能被图形合并绕过。允许合并的类别，只要任一成员缺失，合计就保持为空。
  累计值与比率的系列排序使用最后一个有效值，不跨日期累加。
- 从单款游戏页面进入自助查询时，沿用该游戏范围；可以再选其他游戏，也可以使用跨游戏预设。
  SQL表名只展开字段，不覆盖编辑草稿，不自动运行查询；数据库只读与链接SQL待执行的限制继续保留。
- 多版本同阶段的对象标识包含游戏和版本号，避免不同游戏的同名版本混在一起。
  共用D0–D(n−1)窗口；日历轴仅改变曲线的位置，不改变各自统计日期。评测或在线覆盖不足时，
  相应窗口汇总留空，逐日图保留有效点。图与CSV使用同样的对象、窗口和缺失值。
- 更新前后固定比较D−7–D−1和D0–D6。前后各7个完整评测日且无其他版本更新时才给变化；
  在线另要求前后各7天完整覆盖，时长排除最后一次回填当天。覆盖不足的已有观测标记为不可比。
  评测后仍在玩等后续观察时长不一致的指标不进入更新前后表。
- 版本节奏里的均值来自展示版本各自距上版的有效间隔，首个展示版本可以引用更早的上版日期；
  首个登记版本没有已知前驱，其间隔留空。未开放版本不参与。
  已开放版本数、有效间隔数和间隔均值在指标目录的 `version_window` 事实中定义，自助查询可以复用。
- 玩家结构可以选定版本，并按完整窗口或共同前14/30天查看；共同阶段截到各版本已有的完整评测日，
  时长分布用P25–P75线段与P50圆点，样本数为时长非空的评测数。好评率分母为评价已知样本；
  后续游玩分母为 `post_review_minutes` 非空的合格样本，不拿全部评测数代替分母。
- 视频同龄图支持最多6支手选。覆盖条按所选指标的非空日期计算，空白可能是未观测或该指标缺失，
  共同有效日期是所选视频非空日期的交集，不从累计值回推起跑段。各语区对照表固定展示全部语区，
  不受单语区选择影响，B站与YouTube互动率公式仍不能直接比较。
- 表格每页最多50行，可以浏览全部已取回的结果、搜索和排序；CSV保持原查询完整结果，不受页面搜索排序影响。
  只读SQL取回上限仍为5000行。图表与表格都能下载独立的JSON口径说明；PNG含标题、已选条件、
  实际窗口、可见系列、发布时间和图注。图例开关只影响图与PNG，不改变查询结果或CSV。
- 手机自助查询默认收起指标和筛选，结果靠前；生成SQL可展开查看或带入SQL模式编辑，带入后不自动执行。
  多游戏范围默认按游戏拆分；显式选择“不拆分”时标出合并统计，仍受指标目录的分组限制。
  来源页按失败/无数据、部分成功、过期优先，支持游戏和异常过滤；已停用v2来源的采集记录单独切换查看。

## 快速开始

```powershell
pip install -r requirements.txt
copy .env.example .env               # 填写 YouTube Key 与本机代理（可选）

# 首次：从 v2 数据迁移（只需一次；或者直接运行采集，从空库开始）
python -m store.migrate_v2 --source <v2 项目目录>

python collect.py                    # 采集 + 构建发布包
scripts\serve.cmd                    # 本机查看：http://127.0.0.1:8770/
```

只重建发布包：`python -m store.build`。每次构建会在 `data/backups/` 留一份当天的数据库副本，保留最近 7 天。

### 自动更新（Windows 本机）

```powershell
powershell -ExecutionPolicy Bypass -File scripts\register-tasks.ps1          # 注册
powershell -ExecutionPolicy Bypass -File scripts\register-tasks.ps1 -Status  # 查看状态
powershell -ExecutionPolicy Bypass -File scripts\register-tasks.ps1 -Remove  # 注销
```

| 任务 | 时间 | 做什么 |
|---|---|---|
| GamePulse-Daily | 每天 13:20 | SteamDB 收件箱、Steam、构建号、B 站、YouTube，然后构建；`.env` 里 `GAMEPULSE_AUTO_PUBLISH=1` 时推送到 gh-pages |
| GamePulse-ReviewRecovery | 每天 17:00 | 增量回填近期评测（失败一小时后重试一次） |
| GamePulse-WeeklyReviewBackfill | 每周日 18:00 | 全量校准评测：删评、改评在这时更新 |

永劫端游与其它游戏共用 `collect.py` 和登记/版本/视频配对框架，没有独立页面或独立计划任务。
`python collect.py --game naraka_bladepoint` 更新已登记的双平台视频、Steam 汇总与构建号、官网和月度在线。
评测首次可用 `--only reviews --since YYYY-MM-DD` 回补有界窗口，不冒充全历史基底。
计划任务是否包含当前目录需核对实际动作路径；旧目录的任务成功不代表 v3 已更新。

为什么在本机而不是 GitHub Actions：Actions 的 runner 在境外，B 站接口对境外 IP 有风控，
Steam 商店接口会按 IP 跳区，同一个指标会在不同日子来自不同地区口径。代价是关机时段会漏采，
缺口在图上留空并标出跨了几天，不插值。

### SteamDB 在线人数

SteamDB 的历史直接接口不可用（此前 403 / API 410），数据使用网页 Charts 导出的 CSV。做法：
在 SteamDB 游戏页的 Charts 导出 CSV（文件名形如 `steamdb_chart_3513350.csv`），放进 `data/inbox/steamdb/`，
下次采集会自动按文件名里的 App ID 匹配游戏、按日期合并导入，文件移到 `imported/`；
无法识别的移到 `rejected/`。超过 8 天没有新数据，数据来源页会标为过期。

2026-10-08 实测可使用已登录的 Edge 通过 Windows UI Automation 点击网页 `Download CSV`，
运行 `python -m tools.steamdb_edge_export`（Windows 可选依赖 `pywinauto`）。可以用
`--downloads-dir D:\Download` 指定实际下载目录，`--game naraka_bladepoint` 限定游戏。
工具优先复用现有 Edge 窗口；没有可用窗口时自动启动 Edge，最多等待 30 秒，然后开一个临时标签用网页原生导出。
启动沿用浏览器默认配置，登录或验证由用户完成；不读取凭据、不复制用户配置、不绕过页面验证。
下载后检查日均字段、最新完整 UTC 日期和近期连续覆盖，原文件保留在浏览器下载目录，核验副本进入收件箱。
然后运行 `python collect.py --only steamdb` 导入并构建。运行会短暂占用 Edge 前台，
失败时停止并保留已下载文件；网页验证、登录失效或另存为提示需要用户处理，不承诺无人值守。
图表导出菜单是 SVG，菜单位置以可见图表矩形定位，其余控件按可访问名称操作；网页布局变化时需复核。
四款本机 CSV 已在 2026-10-08 导入，完整日均截至 2026-10-07。

公开发布包含 SteamDB 导出的数据，发布前请自行确认 SteamDB 的使用条款允许这种展示。

## 数据库

初始表结构见 `store/migrations/001_init.sql`，后续迁移在同一目录；设计说明见 [v3-data-layer.md](v3-data-layer.md)。

| 类别 | 表 | 说明 |
|---|---|---|
| 维度（从 YAML 同步） | `game` `version` `video` `video_pair` | 版本窗口不存，由视图推出 |
| 事实（采集器写入） | `review` `online_daily` `steam_daily` `video_obs` `steam_news` `steam_build` `official_news` `steamcharts_monthly` | 一条评测一行；视频一天一行；官网公告按游戏与网址去重；月度在线独立保存 |
| 派生（每次构建重建） | `event` `quality_issue` | 时间轴事件、数据质量提示 |
| 运行记录 | `collection_attempt` `review_run` `review_window_run` `build_meta` | 采集尝试、全历史与有界评测回填覆盖范围 |

写入规则（`store/db.py`，都有测试）：

- 采集**成功**才写事实表；失败只写 `collection_attempt`，已有数据不受影响。
- 同一主键再次写入时，传入的列整体覆盖，包括 NULL：平台隐藏的计数就是未知，不和旧值混用；没传的列不变。
- 列名按表结构校验，拼错直接报错；每批写入在一个事务里，要么全部成功要么全部不写。
- 评测全量回填在一个事务里替换该游戏的评测集合；翻页没完整结束、或者条数异常变少时不替换。

## 口径

- **日期** 一律是 UTC+8 业务日；时间戳一律存 UTC ISO。
- **缺失** 保持为空，不当作 0。覆盖范围内没有评测的日子是真实的 0。
- **比率** 一律"分子合计 ÷ 分母合计"，不对每天的比率求平均。
- **中位数与分位数** `quantile(x, p)` 线性插值（等同 `PERCENTILE_CONT`），p = 0.5 就是标准中位数，
  偶数个时取中间两个值的平均。Python 与浏览器各注册一次，用同一份样例交叉核对。
- **评测数** 按创建日统计当前仍存在的评测（删除的不计入），是"回填重建"口径，与商店显示的累计好评率不同。
  "Steam 总评测数净变化"是另一个指标，不和评测数拼接。
- **在线** 只用 SteamDB 全天平均同时在线。它只代表 Steam 平台，不是 DAU。
  SteamDB 日汇总行的 Players 是某一时点的值，不是峰值（有的日子低于日均），只保存、不展示。
- **版本窗口** 本次 Steam 开放日至下个已开放版本前一天；最新版本开放到今天（按看的人当天的日期计算）。
  已公布未在 Steam 开放的版本不构成窗口。版本对比时开放中的版本只算到最后一个完整评测日。
- **评测后留存参考** 只统计距最后一次回填已满 14 天的评测，"评测后仍在玩"指评测后又玩了 60 分钟以上。
  这是参考，不是留存率。
- **评测语种** 是写评测时选择的语言，不等于玩家所在地区。
- **视频** 只含登记的官方视频（默认只看 `video_pairs.yml` 精选范围）。同一支内容在各语区频道各发一次，
  **播放量不跨语区相加**（指标目录强制按语区分组）。互动率 B 站为（点赞+投币+收藏）÷ 播放，
  YouTube 为（点赞+评论）÷ 播放，公式不同，不直接比较。多数视频是发布后才登记的，
  首次采到时已发布几天会标出来，不从累计值倒推起跑段。

B 站公开计数按 BV 原生投稿或合集提供，有些投稿含多语言分 P，不能从该计数拆出各 P 的播放。
B 站语区表示官方频道服务的语区，不表示只统计中文字幕那一 P；不把多 P 注册为多个独立计数，
也不与 YouTube 各语区相加。对应片核对主片及分 P 时长，不拿合集总时长与单支影片误配。

购买渠道字段（`steam_purchase`、`received_for_free`）在原三款免费游戏上全部是同一个值，没有信息量，所以不做成指标。
永劫曾为买断制，不能套用这个样本结论；当前仍不新增购买渠道指标。

官网公告的日期取页面显示，不直接用网址建稿日；只显示月日的列表以路径年份为参照推定相邻年份，
`date_basis` 保留日期依据，详情页的完整日期优先。分类为标题关键词提示，未自动划定版本窗口。
来源页“官网公告观测”的有效截至日是成功读取列表或文章的业务日，文章发布时间另列；
没有新公告不代表采集过期。列表失败与文章详情失败分别计数，部分成功保留已取到的事实。
回溯模式按归档翻至时间边界，并检查窗口内文章详情；图片型原文摘录保持为空，仍视为已读取原文。

有界评测回填用 `review_window_run` 独立记录覆盖区间。只有完整到达窗口边界才写入，
不会成为全历史基底；`v_review_daily` 只对已覆盖的连续区间补 0，分离窗口之间的缺口不补。
`SteamCharts 月度在线` 保存来源已结束自然月，指标强制按游戏和月份拆分；不拼入 SteamDB 日均，
也不作为某个截断日期窗口的平均在线。近三个月窗口默认同一日号往前推三个月，月底取最后一天。

## 指标目录与自助查询

`config/metrics.yml` 定义事实视图（可以按哪些维度拆分）、维度（中文名、值的显示名、顺序）与指标
（聚合 SQL、单位、格式、规则）。规则由查询生成器强制执行：

- `must_group_by`：必须按这些维度分开（或筛选成单个值），例如视频播放必须按频道语区分开；
- `must_group_by_one_of`：至少按其中一组分开，例如累计播放必须按日期或发布天数；
- `kind: share`：占比，分母是同一行其余维度下的合计。

违反规则时自助查询给出原因，而不是给出一个错误的数。构建时逐条校验：视图存在、维度是视图里的列、
聚合 SQL 能执行。加一个指标只需要改 `metrics.yml`。

自助查询的"直接写 SQL"只接受一条 `SELECT` / `WITH` 查询；数据库是浏览器里的副本，写入也不会影响发布的文件。
浏览器控制台里可以直接用 `gamepulse.rows('SELECT …')`。

## 发布前校验

`store/checks.py` 中任何一项失败都不发布：数据库完整性与外键；每日评测（补 0 后）的合计等于评测行数；
版本窗口首尾相接、互不重叠；每条评测最多属于一个版本窗口；比率在 0–100；精选视频都有语区。
缺采、过期这类真实世界的状况不阻止发布，由质量提示和来源状态如实展示。

公开数据库的导出（`store/export.py`）：评测明细只存一份（按"游戏 + 日期"聚簇），大视图物化成表；
失败原因里的网址、IP 与密钥参数会被去掉；本机专用的小时在线历史不公开。

## 已知限制

- 自有的逐日采集自 2026-09-14 起；更早的在线数据来自 SteamDB 导入，评测来自回填重建。
- 原三款 B 站视频是人工登记的官方视频；永劫另以公开关联接口发现并核验近期样本，不自动改 YAML。
  投稿列表接口 HTTP 412，关联样本无法证明全量覆盖；均不含全部官方内容或创作者生态。
- 2026-09-16 至 09-28 计划任务缺少代理，YouTube 只有少数几天有效观测，这段无法补采；
  多数视频是发布后才登记的，缺少发布初期的数据。
- 玩家规模与评测只跟踪 Steam，不代表游戏的全平台表现，也不能外推到国服；国服公告与视频是内容供给信号。
- 分享链接保存的是筛选条件，不锁定数据版本：打开时看到的是届时最新发布的数据。
- Reddit / Discord / X 未接入：X 对新开发者只有按量付费；Reddit 新 OAuth client 需人工审批；
  Discord 无 Bot 时只能拿到近似在线数且无历史。

## 合规

只使用公开可访问数据。不保存 Cookie、账号或 Authorization header；API Key 只从 `.env` / 环境变量读取，
不写进配置或数据库，公开数据库导出时还会去掉失败原因里的请求参数；不破解验证码、不绕过登录、不做反检测；
遵守公开接口频率与平台服务条款。

本项目是独立研究原型，不代表任何平台或游戏公司的官方系统。
