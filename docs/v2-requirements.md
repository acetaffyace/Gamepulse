# GamePulse v2 需求定义：长线运营多平台情报看板

**文档状态：** 需求确认稿（待你拍板）
**日期：** 2026-09-14
**基线：** 当前 game-ops-radar MVP（Steam + B 站，3 款游戏，单页 ECharts 看板）
**目标：** 扩展到多平台传播数据 + 可自定义看板 + 无人值守自动更新

---

## 0. 一句话结论

你现在缺的**不是采集能力**——Steam 和 B 站两条链路已经跑通且数据质量口径做得很干净。
真正缺的是三件事：

1. **已采到的数据没被用起来**（B 站点赞/投币/收藏/评论已入库但看板不显示；Steam 评测里的玩家游戏时长已落盘但没算过）；
2. **没有第二个海外传播源**（YouTube），导致 Steam 海外盘的传播端是空白；
3. **没有调度器和可配置前端**，看板是硬编码的四条轨道，改一个指标要改代码。

下面按「现状 → 差距 → 可行性 → 决策」展开。

## 1. 现状盘点

### 1.1 已经具备的资产（不要重写）

| 模块 | 状态 | 说明 |
|---|---|---|
| `collectors/steam.py` | 可用 | 在线人数、评测汇总、价格（已证不可用）、官方公告 |
| `collectors/steam_reviews_backfill.py` | 可用 | 游标翻页回填全部存活评测，自动按总数推算页数 |
| `collectors/bilibili.py` | 可用 | view/danmaku/reply/like/coin/favorite/share **七项全采**，并复核 `owner.mid` 防搬运号 |
| `collectors/bilibili_discover.py` | 可用 | 用 `archive/related` + mid 过滤半自动发现官方新视频（绕开有风控的搜索接口） |
| `pipeline/` | 可用 | 指标、质量检查、快照组装、对比页生成 |
| `dashboard/` | 可用 | 零依赖静态页 + ECharts，四轨道共享日期轴 |
| 数据资产 | 已积累 | 3 款游戏；鸣潮评测历史 444 天、绝区零 90 天、异环 69 天；B 站 43 条已核验官方视频 |

### 1.2 已经被实测否定的路（不要再试）

| 方案 | 结论 |
|---|---|
| Steam `appdetails` 拿价格 | 三款游戏全部返回 `success:false`，价格轨道永久空 |
| SteamDB 拿历史在线曲线 | 403 / API 410，不可程序化访问 |
| SteamCharts | 未收录这几个 App |
| B 站搜索接口自动发现视频 | 有风控，项目已明确不用 |
| Steam 在线人数历史回填 | **不存在任何合法可得的历史源**，只能从今天起逐日积累 |

### 1.3 一个必须先说清楚的结构性事实

三款游戏的 Steam 评测语言构成：

| 游戏 | 评测总量 | 简体中文占比 | 第一大语种 |
|---|---|---|---|
| 绝区零 | 13,940 | **0.4%** | English 49% |
| 鸣潮 | 32,417 | **1.4%** | English 64% |
| 异环 | 5,287 | **0.2%** | English 53% |

**Steam 侧是海外盘，B 站侧是国内盘，两者不是同一批人。**
所以看板不能把它们合成一个"综合热度"。v2 的信息架构必须显式分成
**海外盘（Steam + YouTube + Reddit/Discord）** 与 **国内盘（B 站）** 两条叙事线，
共享同一条版本时间轴——这恰好也是接入 YouTube 的最大理由：
YouTube 观众和 Steam 玩家是同一群人，两者放一起才有因果讨论的基础。

## 3. 数据源可行性与代价

### 3.1 Steam（免费，无 Key，已验证）

**新增可做的（优先级从高到低）：**

1. **玩家结构分析（数据已在本地，只差计算）**
   回填的每条评测都带 `playtime_at_review`（分钟）、`playtime_forever`、`steam_purchase`。
   可直接算出：
   - 每日新增评测者的**游戏时长中位数** → 区分「首日冲动评测」与「长线玩家评测」；
   - **版本更新后的评测者时长分布突变** → 老玩家回流 vs 新玩家涌入的代理信号；
   - `playtime_forever − playtime_at_review` → 评测后是否继续玩（**留存代理**，这是公开数据能拿到的最接近留存的东西）；
   - `steam_purchase=false` 占比 → 非 Steam 渠道激活/赠送比例。
   > 这是整个项目里最像"游戏运营分析"而不是"数据搬运"的部分，也最适合放进作品集。

2. **小时级在线采样** → 日峰值、日谷值、峰谷比、峰值出现时刻（时区分布 → 玩家地域结构佐证）。
   成本：24 次/天/游戏 × 3 游戏 = 72 次轻量请求/天，远低于任何限流阈值。

3. **构建更新时间**：`https://api.steamcmd.net/v1/info/{appid}` 返回 `buildid` + `timeupdated`，
   免费、无 Key，可拿到不依赖公告文案的真实更新时点。**需 P0 阶段实测确认可用**。

4. **完整语种结构时间序列**：回填数据已足够，只是当前只导出了 top-5。

**边界：** 价格永久不可用；在线历史永久不可回填。

### 3.2 B 站（免费，无 Cookie，已验证）

**核心工作是把已采数据用起来**，并建立互动率指标体系：

| 指标 | 公式 | 含义 |
|---|---|---|
| 播放日增 | `view[t] − view[t-1]` | 长尾热度 |
| 互动率 | `(like+coin+favorite)/view` | 内容质量，**跨视频可比，不受量级干扰** |
| 三连率 | `coin/view`、`favorite/view` | 投币成本最高 → 认可度最强信号 |
| 讨论密度 | `reply/view`、`danmaku/view` | 争议度 / 观看深度 |
| 首 7 日爬坡曲线 | 发布后 D1..D7 的日增形态 | **角色 PV 之间横向对比的标准口径** |

> 首 7 日曲线要求视频**在发布当天就进采集表**。现有 43 条视频大多是事后登记的，
> 首 7 日已经错过。所以 P0 就要把 `bilibili_discover.py` 接进日常调度，新视频自动进候选。

**边界：** 播放量只有当前累计值，没有历史曲线；登记制不覆盖创作者视频。

### 3.3 新平台

| 平台 | 可行性 | 代价 | 建议 |
|---|---|---|---|
| **YouTube** | ✅ 最优 | Data API v3 免费 10,000 units/天。`videos.list?part=statistics` 可**一次批 50 个 ID，只花 1 unit**；用频道 uploads 播放列表发现新视频（`playlistItems.list` = 1 unit）。日常追踪 200 个视频 ≈ **5 units/天**，配额用不掉 0.1% | **P1 必做**。字段：viewCount / likeCount / commentCount（dislike 已被 YouTube 下线，拿不到）。**优势：官方频道新视频可自动发现，不像 B 站要人工登记** |
| **Reddit** | ⚠️ 可行但有门槛 | 免费层 100 QPM/OAuth client，但 2025 年底起**新 client 需人工审批**，且 2026-08 官方announced 将逐步收紧公共 Data API | **P2**。只做低频、低量指标：subreddit 订阅数、日发帖量、版本日的帖子量突增。不做评论抓取 |
| **Discord** | ⚠️ 信号很弱 | 无需 Key 的只有 `widget.json` 的 `presence_count`（近似在线人数），且**需服务器开启 widget**；拿成员总数需要 bot 入服 | **P3 或不做**。单一近似在线数，无历史，性价比最低 |
| **X** | ❌ 已不免费 | 2026-02-06 起新开发者**只有 pay-per-use**，无免费层，Basic $200 档已对新用户关闭。post read ≈ $0.005/条、user read ≈ $0.010/次 | **建议不做**。若坚持，最低成本方案是只追官方账号的 follower 数（1 次 user read/天 ≈ $0.30/月），不追单条推文 |

## 4. 需要你拍板的 6 个决策

我给了推荐值，你可以直接说"按推荐来"。

| # | 决策 | 选项 | 我的推荐 |
|---|---|---|---|
| **D1** | **自动更新跑在哪** | (a) 本机 Windows 任务计划程序 (b) GitHub Actions (c) 云服务器 | **(a) 本机**。GitHub Actions 的 runner 在境外，B 站接口对境外 IP 有风控、Steam 商店接口也会跳区，会毁掉数据一致性。本机跑 + 数据提交回仓库最稳。代价是关机就漏采（用 `missed_days` 标记，不补 0） |
| **D2** | **看板技术栈** | (a) 保留零依赖静态 HTML+ECharts (b) 换 Next.js+TS (c) 换 Streamlit (d) Grafana | **(a) 保留并重构成配置驱动**。现在这套的最大优点是双击即开、无构建、易截图进作品集。"自定义"用一个 `dashboard/layout.json` + 轨道注册表实现，不需要引入前端框架。除非你要做 D3=多人访问 |
| **D3** | **谁会打开这个看板** | (a) 只有你本机 (b) 放到公网给面试官看 | **(a) 本机为主，公网留一个静态导出**（纯静态页可直接扔 GitHub Pages，数据走 JSON）。会影响是否要做隐私/合规加固 |
| **D4** | **"自定义"到底指什么** | 见 §5 的 L1/L2/L3 三档 | **L2**：轨道可增删换序、指标可切换、阈值/配色可调、视图可保存分享——但不做拖拽式 BI |
| **D5** | **游戏范围** | 维持 3 款 / 扩到 8-10 款（原神、星铁、崩3、明日方舟、无限暖暖…） | **先扩到 6 款**（加原神、星穹铁道），刚好覆盖"米哈游 vs 库洛 vs 完美世界"三方对照，且 Steam 上都有；再多会让 B 站人工登记成本失控 |
| **D6** | **仓库位置** | 留在 `简历/game-ops-radar/`（当前未被 git 跟踪）/ 拆成独立仓库 | **拆成独立仓库**。它是作品集主角，埋在简历仓库里既不好展示，也会被简历仓库的 `.gitignore` 规则误伤 |

## 5. "自定义" 的三档定义（对应 D4）

| 档位 | 能力 | 实现成本 |
|---|---|---|
| **L1 轻** | 选游戏、选时间范围、开关已有轨道、切换绝对值/指数化 | 2 天 |
| **L2 中（推荐）** | L1 + **轨道注册表驱动**：任意指标可加为一条轨道、轨道可排序/删除/设高度；对比模式任选 2-3 款游戏；阈值线与告警可配；视图配置存 localStorage 并可导出成 URL 分享；导出 CSV / PNG / 一页周报 | 5-7 天 |
| **L3 重** | L2 + 拖拽布局、自定义公式编辑器（`(like+coin)/view` 这种表达式用户自己写）、多看板页签 | 15 天+，且会把这个项目从"运营情报工具"变成"半个 BI 产品"，作品集反而失焦 |

**L2 的关键设计：** 一条轨道 = 一份声明式配置

```yaml
- id: bili_interaction_rate
  title: B 站互动率
  source: bilibili
  metric: (like + coin + favorite) / view
  chart: line
  unit: percent
  color: slot3
  height: 120
  caveat: 登记视频集合，非全站
```

前端只认这份配置，加指标不改图表代码——这直接满足"自定义很多东西"，
也顺带解决了当前"四条轨道写死在 app.js 里"的问题。

## 6. 自动更新方案（对应 D1）

```
每小时  :05   steam_online.py        → 在线人数采样（轻，3 游戏 72 次/天）
每日  13:20   collect.py             → Steam 汇总 + B 站 + YouTube 全量
每日  13:40   *_discover.py          → B 站/YouTube 官方新视频发现 → 写入候选表
每周日 14:00  steam_reviews_backfill → 刷新评测历史（重，不必每天）
每次采集后    build_snapshot + quality → 失败/异常写 alerts.json，看板顶部红条显示
```

- 幂等：当天重复运行覆盖当天记录，可安全补跑（现有 `upsert_series` 已保证）；
- 漏采：关机导致的缺天标记 `missed`，曲线断开，**不插值、不填 0**（沿用现有原则）；
- 告警：连续 2 次失败 / 超 48h 无有效快照 / 数值倒退 → 看板顶部横幅 + 日志；
- 新视频发现**只产出候选**，版本与角色归属仍需你人工确认（沿用现有原则，因为角色 PV 常早于版本更新日 5-12 天，机械按日期归类会错）。

## 7. 相似作品参考

| 作品 | 可借鉴 | 不可借鉴 |
|---|---|---|
| [SteamDB](https://steamdb.info/charts/) | 信息密度、版本/构建时间线、工具感 | 数据源（已 403）；不要抄 UI |
| [SteamCharts](https://steamcharts.com/) | 月度峰值/均值的呈现方式 | 覆盖不到你的三款游戏 |
| [SteamSpy](https://steamspy.com/) | 拥有者数估算的免责声明写法 | 估算值不可当事实 |
| [Metaplay LiveOps Dashboard](https://docs.metaplay.io/liveops-dashboard/introduction-to-the-liveops-dashboard) | 商业 LiveOps 看板的信息架构 | 它是内部数据系统，你只有公开数据 |
| [Rawbbit](https://rawbbit.one/)（Apache-2.0） | 开源游戏分析的工程结构（对象存储 + ClickHouse） | 面向自家埋点，不采第三方平台 |
| [Heroic Labs Satori](https://heroiclabs.com/satori/) | 事件日历 + 趋势联动的交互模型 | 同上 |

**结论：没有现成项目覆盖你的组合**（公开多平台传播数据 + 版本事件轴 + 自定义看板）。
搜索结果里最接近的是「自建 poller → ClickHouse/Postgres → Grafana/Metabase」这条通用路线，
但它换不来你要的"版本轴 + 角色 PV + 中外双盘"叙事，且引入了不必要的数据库依赖。
**现有 JSON/JSONL + 静态页的架构在这个数据量级（年增 ~50MB）是更优解，建议保留。**

## 9. 明确不做（沿用 MVP 原则）

- 不推断 DAU、收入、留存率、付费率、LTV——只能用公开代理指标并标注为 proxy；
- 不登录、不带 Cookie、不破验证码、不做反检测、不绕风控；
- 不用模型或随机数补齐历史数据，缺失就是断点；
- 不把时间上的共现写成"版本导致在线上涨"的因果结论；
- 不声称覆盖全网讨论量——B 站是"登记视频集合"，Steam 是"平台内评测"；
- 不做玩家级画像、用户识别或社区自动操作。
