# v3 数据层设计

日期：2026-09-29。状态：已确认（第 11 节全部按推荐）。范围：数据怎么存、指标怎么定义、采集怎么写入、网站怎么发布。
前端页面的设计另写文档。可行性已由 [spike](../spike/README.md) 验证。

---

## 1. 一句话

**人工维护的内容留在 YAML，机器采集的数据进 SQLite，指标只用 SQL 定义一次；
发布时导出一份压缩的数据库文件，网页直接在浏览器里查询。**

## 2. 目标与不做的事

要做到：

1. 同一个指标只有一处定义。看板卡片、图表、自助查询、导出，数字全部一致。
2. 支持自助查询：选指标、维度和筛选条件出图，不用提前生成数据。
3. 新增一款游戏只需改配置并运行采集，不改代码。
4. 采集失败不会覆盖已有的好数据；缺失的数据保持为空，不当作 0。
5. 仓库不再随数据变大：数据库文件不进 main 分支。
6. 校验真正独立：用手算的小样例测试 SQL，不再"用被测函数验证自己"。

这一版不做：服务端、登录、多人写入、评测正文采集、小时级在线采样。

## 3. 整体流程

```
 人工维护（git 管理）          机器采集（笔记本白天运行）
 config/*.yml                  collectors/*.py
 游戏 / 版本 / 视频登记 / 配对   Steam / B 站 / YouTube / SteamDB 导入
        │                               │
        └──────────┬────────────────────┘
                   ▼
        data/gamepulse.sqlite  ← 本机唯一数据源（不进 git）
                   │  构建：同步配置 → 刷新派生表 → 校验
                   ▼
        发布包 public/
          gamepulse.<hash>.sqlite.gz   完整可查询的数据库
          summary.json                 首屏用的小汇总
          manifest.json                版本号、生成时间、各来源截至日期
                   │
                   ▼
        gh-pages 分支（每次覆盖，只保留最新）→ GitHub Pages
```

## 4. 表设计

### 4.1 维度表（从 YAML 同步，每次构建重建）

| 表 | 一行是什么 | 主键 | 主要字段 |
|---|---|---|---|
| `game` | 一款游戏 | game_id | 名称、厂商、Steam AppID、Steam 上线日、颜色 |
| `version` | 一个版本 | game_id + version_id | 开放日（UTC+8）、状态（已开放/已公布）、来源类型、来源链接、备注 |
| `video` | 一支登记的官方视频 | platform + video_id | 游戏、标题、频道、频道语区、发布日、内容类型、版本归属、角色、配对 ID、是否核验为官方 |
| `video_pair` | 同一内容在不同平台/语区的一组视频 | pair_id | 游戏、内容类型、版本、角色 |

版本窗口（开放日到下个版本前一天）不单独存，由视图从 `version` 推出。

### 4.2 事实表（采集器写入）

| 表 | 一行是什么 | 主键 | 字段 | 来源 |
|---|---|---|---|---|
| `review` | 一条 Steam 评测 | review_id | 游戏、创建日（UTC+8）、好评/差评/未知、语种、写评测时时长、总时长、是否 Steam 购买、是否免费获得、最后一次见到它的采集时间（用来算"评测后又玩了多久"） | 评测回填 |
| `online_daily` | 一款游戏一天的在线 | game_id + date | 日均在线、峰值在线、导入文件名 | SteamDB 导出 |
| `steam_daily` | 一款游戏一天的官方汇总 | game_id + date | 总评测数、总好评数、评分描述、当时在线（仅作参考） | Steam 接口 |
| `video_obs` | 一支视频一天的累计计数 | platform + video_id + date | 播放、点赞、评论、投币、收藏、分享、弹幕；拿不到的保持空 | B 站 / YouTube |
| `steam_news` | 一条 Steam 公告 | game_id + gid | 日期、标题、链接、来源频道、识别出的类型和版本号 | Steam 接口 |
| `steam_build` | 一天观测到的构建号 | game_id + date | 构建号、构建更新时间 | SteamCMD |

### 4.3 派生表（每次构建由程序生成，不手改）

| 表 | 一行是什么 | 怎么来 |
|---|---|---|
| `event` | 一个时间轴事件 | 版本更新（以版本表为准）、版本预告、构建号变化、官方视频发布。字段：日期、类型、版本号、标签、证据来源、来源链接、是否版本分界 |
| `quality_issue` | 一条数据质量提示 | 构建时的检查结果：缺采日、数据过期、总评测数异常下降、视频播放量倒退、视频不属于官方账号、公告里有但版本表没有的版本、版本跳号 |

公告类型的识别规则（正则）仍然用 Python 写，结果存进 `event`，其他部分都用 SQL 读取。

### 4.4 运行记录表

| 表 | 一行是什么 | 用途 |
|---|---|---|
| `collection_attempt` | 某来源对某游戏的一次采集尝试 | 状态（成功/部分成功/失败/跳过/未配置）、期望数、成功数、错误原因。数据来源页和"截至日期"都从这里算 |
| `build_meta` | 一次构建 | 构建号、生成时间、表结构版本 |

**关键规则：采集失败只写 `collection_attempt`，不碰事实表。** 所以"失败覆盖好数据"的问题从结构上消失了，
不再需要 v2 那套"保留旧观测"的合并逻辑。

### 4.5 约定

- 日期一律存 UTC+8 业务日，格式 `YYYY-MM-DD`；时间戳一律存 UTC ISO 字符串。
- 每张事实表都在 `fact_source` 表里登记来源类别：直接采集、回填重建（评测）或第三方（SteamDB、steamcmd.net）。
  同一张表的数据来源类别相同，所以按表登记，不在每一行重复存。页面和自助查询按这张表显示来源标注。
- 拿不到的值存 NULL，不存 0。好评/差评未知也存 NULL，不算差评。
- 表结构版本记在 `PRAGMA user_version`，升级用编号的迁移脚本（`store/migrations/001_init.sql` ……）。

## 5. 指标层：视图 + 指标目录

### 5.1 视图（把"怎么算"固定下来）

| 视图 | 作用 |
|---|---|
| `v_version_window` | 每个已开放版本的起止日 |
| `v_review` | 评测 + 所属版本 + 更新后第几天 + 时长段（<2h / 2–20h / 20–100h / 100h+） |
| `v_review_daily` | 每游戏每天的评测数、好评、差评 |
| `v_online_daily` | SteamDB 日均在线 + 所属版本 + 更新后第几天 |
| `v_video` | 视频 + 归属版本。已人工确认的版本优先；未确认的按发布日落在哪个版本窗口来归属，并注明依据。只包含身份核验为官方、且在 `video_pairs.yml` 精选范围内的视频 |
| `v_video_daily` | 视频每日增量；跨缺采日的差值标明跨了几天，不冒充单日 |
| `v_video_age` | 视频"发布后第 N 天"的累计值，用于同龄比较；同时给出首次采到时视频已发布几天（判断有没有缺起跑段） |
| `v_review_language_week` | 按周（游戏：日历周；版本：更新后第几周）统计的语种构成 |
| `v_source_freshness` | 每个来源最后一次成功时间、有效数据截至日期 |

发布时，`v_review` 这类数据量大的视图会直接存成表并加索引（spike 实测查询快一倍）。

### 5.2 指标目录（让自助查询和固定看板共用一套定义）

新增 `config/metrics.yml`，每个指标一条，构建时校验并写入数据库的 `metric` 表：

```yaml
- id: review_count
  name: 评测数
  fact: v_review            # 从哪个视图取
  agg: COUNT(*)             # 怎么聚合
  unit: 条
  dimensions: [game, version, day_index, date, language, playtime_band, voted_up]
  note: 按创建日统计仍存续的评测；删除的不计入

- id: positive_rate
  name: 好评率
  fact: v_review
  agg: 100.0 * SUM(voted_up = 1) / NULLIF(SUM(voted_up IS NOT NULL), 0)
  unit: '%'
  dimensions: [game, version, day_index, date, language, playtime_band]

- id: playtime_median
  name: 评测时时长中位数
  fact: v_review
  agg: median(playtime_at_review)     # 由查询生成器展开为窗口函数写法
  unit: 小时
  scale: 1/60
```

自助查询页和固定看板页都用"指标 + 维度 + 筛选"生成同一种 SQL：

```sql
SELECT <维度>, <指标聚合> FROM <fact> WHERE <筛选> GROUP BY <维度>
```

所以固定看板上的数字和自助查询出来的数字不可能不一致。

指标目录还负责挡住"算得出来、但没有意义"的组合：

- **不能跨语区相加**：同一支 PV 在 4 个语区频道各发一次，播放量加起来等于同一支片子算了 4 遍。
  视频指标标记 `must_group_by: [locale]`，查询生成器会强制按语区分开。
- **比率不能相加**：好评率、互动率一律按"分子合计 ÷ 分母合计"重新计算，不对每天的比率求平均。
- **数据源不同的数字不直接比较**：比如 SteamDB 日均在线和 Steam 瞬时在线，不放在同一个指标里。
- 构建时逐条校验：每个指标的 SQL 能执行，声明的维度都存在。
  这替代了 v2 的"轨道字段能在快照里取到值"检查。

### 5.3 第一批指标（与 v2 对齐）

- **评测**：评测数、好评数、差评数、好评率、日均评测数、评测时时长中位数 / 25 分位 / 75 分位、各时长段占比、各语种占比（前 8 种加"其他"）、非 Steam 购买占比、免费获得占比。
- **评测后留存参考**：评测后又玩的时长中位数、评测后仍在玩的占比（评测后又玩了 60 分钟以上）。距评测不满 14 天的不参与计算。v2 算了这些但页面没用上，v3 只是放进指标目录，可以查询。
- **在线**（SteamDB）：日均在线、峰值在线、窗口均值。
- **Steam 存量**：全局累计好评率、总评测数净变化。
- **视频**：播放、点赞、评论、投币、收藏、分享；播放日增、互动率（与 v2 一致：B 站 `(点赞+投币+收藏)/播放`，YouTube `(点赞+评论)/播放`）；发布后第 N 天累计。
- **事件**：版本更新、构建号变化、公告类型。

### 5.4 借这次机会统一的口径

排查 v2 时发现同一件事有多种算法，v3 各只保留一种：

| 问题 | v2 现状 | v3 统一为 |
|---|---|---|
| 中位数 | 4 种算法：取中间偏上那个、取两个中间值的平均、按位置四舍五入取值、"每日中位数的中位数" | 标准中位数：个数为偶数时取中间两个值的平均。一律从明细算，不再算"中位数的中位数" |
| 评测数的来源 | 回填明细和"Steam 总评测数的每日净变化"两套拼接，还要标注用的是哪一套 | 评测数只从评测明细来。"总评测数净变化"单独作为一个指标，不再拼接 |
| 回填范围 | 玩家结构只读全量回填，每日评测还合并了增量回填，两边数字可能对不上 | 都读同一张 `review` 表 |
| 在线口径 | 某种旧模式下，同一列数字有时是日均、有时是零点瞬时值 | 只有 SteamDB 日均和峰值两列，名字就是含义 |
| 游戏对象的"第 0 天" | 用的是评测回填最早的日期 | 用 Steam 上线日（`games.yml` 的 `steam_release`） |
| 好评率的比较 | 有的地方先对每天的比率求平均，有的地方先合计再相除 | 一律先合计再相除 |

v2 里算了却从没显示、或者早已没有数据的内容，v3 不再生成：价格和折扣、小时在线统计、
和 B 站视频列表完全重复的 `character_videos`、重复存放的新鲜度字段等。

## 6. 采集器怎么改

| 采集器 | 改动 |
|---|---|
| 公共部分 `common.py` | 删掉文件锁、原子写、读-合并-重写那一套（约 150 行），换成 `store.write(table, rows)`：一个事务内 `INSERT … ON CONFLICT DO UPDATE` |
| `steam.py` | 写 `steam_daily`、`steam_news` |
| `steam_build.py` | 写 `steam_build` |
| `bilibili.py` / `youtube.py` | 写 `video_obs`；视频的元数据仍以 YAML 登记为准 |
| `steam_reviews_backfill.py` | 增量：新评测直接写入 `review`。每周全量：在一个事务里替换该游戏的评测集合，等同 v2 的"存续评测"口径，删评和改评都会在这时更新 |
| `steam_online.py`（小时采样） | **停用**。在线只用 SteamDB |
| SteamDB 导入 | 把导出的 CSV 放进 `data/inbox/steamdb/`，每次采集开始时自动导入并归档；网页显示"在线数据截至某日" |
| `*_discover.py` | 不变，仍然只产出候选、需要人工确认后才进 YAML |

每次运行都往 `collection_attempt` 写一条记录。原始接口响应仍按现在的方式存到 `data/raw/`，方便以后重算。

SQLite 同一时间只允许一个程序写入，其他写入会排队等待（设置等待超时 30 秒）。现在的任务都是顺序执行的，这个限制不构成问题。

## 7. 构建与发布

`python -m gamepulse build`（名称待定）依次做：

1. 把 YAML 同步进维度表；校验版本表、视频登记和配对表的一致性。
2. 刷新派生内容：公告类型识别、版本事件。
3. 运行校验（任何一项失败就停止发布）：
   - 约束检查：主键、外键、日期格式、非负计数；
   - 口径自检：窗口内的评测数合计等于逐日相加，好评率落在 0–100；
   - 新鲜度：每个来源的截至日期写进 manifest，超期只标记、不阻止发布。
4. 导出公开数据库：用 `VACUUM INTO` 复制一份，把大视图存成表、加索引，去掉运行日志里不需要公开的字段；压缩成 `.sqlite.gz`，文件名带内容哈希。
5. 生成 `summary.json`（首屏卡片和主图用的少量数据）和 `manifest.json`。
6. 发布到 `gh-pages` 分支：每次只保留最新一份，避免仓库膨胀。发布需要你确认过的 git 推送权限。

网页先读 `manifest.json`，再按里面的哈希文件名加载数据库，所以不会读到一半新、一半旧的数据。
这替代了 v2 的 `releases/<批次号>/` 加索引切换那套机制。

**备份**：本机数据库每天自动留一份副本，保留最近 7 天；公开的数据库本身也是一份异地副本。原始响应 `data/raw/` 可以用来重建。

## 8. 从 v2 迁移

1. 用 spike 的导入脚本扩展出正式的一次性迁移：把 v2 的 JSONL 和原始评测全部导入。
2. 口径对照测试：对所有重叠的指标，SQL 结果必须和 v2 快照完全一致。已验证的有每日评测、版本窗口、好评率、在线窗口均值、中位时长，会逐步补全到视频和数据来源。
3. 过渡期间，v2 在原目录照常采集和发布；v3 定期从 v2 目录重新导入，直到采集器也切换过来。
4. 切换时：v3 的采集器接管计划任务，v2 的采集停止，Pages 改为从 `gh-pages` 发布。

## 9. 测试

- **SQL 视图**：用内存数据库和手写的小样例（比如 5 条评测、2 个版本），期望值手算写在测试里。这是真正独立的核对。
- **写入规则**：失败不覆盖、NULL 不变成 0、重复运行结果不变、全量替换在一个事务里完成。
- **迁移对照**：v3 对 v2 的口径一致性（只在过渡期保留）。
- **浏览器**：沿用 Playwright，检查加载、查询、断网和旧数据提示。

| v2 | v3 |
|---|---|

## 11. 已确认的决定（2026-09-29，全部按推荐）

第 2 条是唯一需要在项目之外核实的事项：公开发布前由项目作者确认 SteamDB 条款。

1. **v2 那几天的小时在线数据**：不再展示，但保留在数据库里（成本几乎为零）。可以吗？
2. **SteamDB 数据公开发布**：需要你确认 SteamDB 的使用条款允许在公开网站展示它的导出数据。
3. **评测每周全量替换**：删评和改评在每周全量时才更新，平时只追加新评测，与 v2 一致。可以吗？
4. **发布方式**：改为推送到 `gh-pages` 分支，每次覆盖。需要本机能 `git push`。
5. **命令入口**：保留 `python collect.py` 这个名字（习惯不变），内部改为写数据库。
6. **中位数改成标准算法**（见 5.4）：个数为偶数时，部分中位时长会和 v2 差几分钟。迁移对照时这一项按新算法单独核对。可以吗？
7. **游戏对象的第 0 天改为 Steam 上线日**（见 5.4）：鸣潮的起点会从 2025-04-29 变成 2025-04-28。可以吗？

## 12. 实施顺序

每一步都能单独验证，完成后再进下一步：

1. `store/`：表结构、迁移、写入函数，以及它们的测试。
2. 正式迁移脚本 + 口径对照测试（v3 数据库的数字 = v2）。
3. 视图 + 指标目录 + 查询生成器，以及手算样例测试。
4. 构建与发布（先发布到本地目录，确认后再推 `gh-pages`）。
5. 采集器逐个改为写数据库；SteamDB 导入改为放入文件夹即可。
6. 前端改造（另写设计文档）。
