## 偏离设计的决定

### 分位数用自定义聚合函数，不在查询生成器里展开（步骤 3）
设计 5.2 原本打算由查询生成器把 `median()` 展开成窗口函数写法。改为在 Python 和浏览器两端都注册
同名聚合函数 `quantile(x, p)`（线性插值，p=0.5 即标准中位数）：
- 查询生成器只需拼接字符串，不需要为中位数单独改写整条 SQL；
- 自助探索的"直接写 SQL"模式里，用户也能直接写 `quantile(playtime_at_review, 0.5)`；
- 两端实现各十几行，用同一份样例文件交叉核对。

代价是：公开的数据库文件放到别的 SQLite 工具里打开时，没有这个函数。这可以接受。

### 不生成 summary.json（步骤 4）
设计第 3、7 节打算额外生成一份首屏小汇总。但首屏的数字必须和自助查询一致，
如果另外生成，就等于同一个口径有两份产物。spike 实测数据库在 20 Mbps 下 0.9 秒就能查询，
所以改为：首屏先显示骨架，同时预加载数据库，就绪后直接查询。
如果日后数据量变大、首屏变慢，再按指标目录生成预聚合结果。

### 前端测试发现的问题（步骤 6）
端到端测试第一次运行就发现两个真实问题：
- 自助查询"直接写 SQL"的默认示例以注释开头，而只读检查要求以 SELECT 开头，默认示例自己被拒绝，
  线上打开这一页会直接报错。检查改为跳过开头的注释。
- 视频页的 5 个语区按钮在 390px 手机宽度下不换行，页面横向溢出 21px。

截图检查还发现同龄对比图只有图例、没有线：YouTube 在 v2 期间大部分日子采集失败，
数据点前后都缺，而折线默认不画圆点，孤立的点就看不见。改为对有孤立点的系列显示圆点，缺口仍然不连线。

### 独立审核（步骤 7）
请两个独立的审核代理分别审数据层和前端，只读、用真实数据和无头浏览器复现。结论：8 条设计原则在正常运行下都成立，
页面数字与独立 SQL 核对一致，没有 XSS 与 SQL 注入；但找出了下面这些真实问题，已全部修复并补了对应的回归测试。

数据层：
- **续翻的全量回填会删掉新评测**（中）：全量从 48 小时内的旧进度续翻时，看不到翻页开始之后的新评测，替换时把它们当成已删除，
  还把这些日子记成"完整的 0 条"。改为只替换翻页开始之前创建的评测，覆盖范围也只到开始那天。
- **两次构建同时运行会发布坏掉的发布包**（中）：manifest 可能指向已被另一次构建清理掉的数据库。构建改为跨进程串行，临时文件名唯一。
  用去掉锁的版本验证过：测试三次都会失败。
- 未配置的来源显示成"过期"；认出了游戏的 SteamDB 失败导入在来源页看不到；UTC 写的版本开放时间差一天；
  SteamDB 导出的最后一天不完整却被导入；标为已开放的未来版本得到负长度窗口；敏感信息过滤漏掉带账号的代理地址等格式。

前端：
- **"只读 SQL"并不只读**（高）：`WITH … DELETE` 能通过文字检查。改为数据库打开后立即设 `PRAGMA query_only`，
  写语句由 SQLite 本身拒绝；链接里带来的 SQL 不再自动执行；结果最多 5000 行（也让无限递归的查询停下来）。
- **累计播放能按日期相加**（高）：每天纳入的视频集合不同，数字的跳动其实是"多追踪了几支视频"。指标目录改为必须按视频拆开。
- **比率能画成堆叠图**（高）：三款游戏好评率叠到 250%。不可相加的指标拒绝堆叠。
- 总览拿数据覆盖不到的前一段时间算变化；版本对比在两边在线覆盖天数不同时仍给差值；A、B 可能被选成同一个版本；
  非法的天数参数显示荒谬内容；语种颜色随排名变化；点"时间范围"文字会误触第一个按钮（按钮组外层用了 label）；
  手机上 SQL 页溢出；自助查询横轴跳过缺数据的日期、让折线直接连过去；大结果集渲染慢；CSV 公式注入。

## 勘误

### SteamDB 的 Players 不是峰值（步骤 2）
设计里把 SteamDB 日汇总行的 Players 写成了"峰值在线"。核对数据发现，三款游戏分别有 31、28、31 天的
Players 低于当天的日均在线，而峰值不可能低于均值，所以它只是某个时点的值。
列名改为 `point_players`，不再作为峰值展示，也不进入第一批指标。

### 购买渠道字段没有信息量（步骤 3）
设计 5.3 列了"非 Steam 购买占比""免费获得占比"。实际数据里 80,296 条评测全部是
`steam_purchase = 1, received_for_free = 0`：三款都是免费游戏，Steam 一律记为购买。
这两个字段仍然存在表里（以后接入付费游戏时有用），但不放进指标目录，避免显示一个像结论的 0%。

### 公开数据库一度膨胀到 5 MB（步骤 4）
第一次导出压缩后 5.16 MB，是 spike 的 4.7 倍。逐表删除测量后发现：评测明细存了两份
（`review` 原表 + 物化后的 `v_review`），物化表还带着网页用不到的长时间戳列，外加 3 个索引。
改为把评测视图拆成两层：耗时的"评测 × 版本"区间连接 `v_review_base` 按"游戏 + 日期"聚簇存成表，
只留用得到的列，然后删掉原表；周、时长段等换算仍是视图。压缩后降到 1.30 MB，查询反而更快
（全部版本中位时长 215 → 70 ms）。口径表达式仍只在 `views.sql` 写一次。

### 评测回填的断点格式（步骤 5）
v2 的翻页进度文件存的是"拍平"后的行（时长在顶层），v3 存接口原样的评测（时长在 `author` 下）。
如果切换当天正好有 v2 留下的未完成进度，v3 会接着翻，读到的时长全部为空。
进度文件的查询条件里加了格式版本号，旧进度不会被续用；解析函数也同时兼容两种格式。

- 官方更新公告登记六个已开放日期补丁，另登记一个未开放的赛季预告，后者不成为比较边界。
- 登记 28 支 B 站、69 支全球 YouTube 官方视频，核对 16 组对应内容；默认精选查询与每日采集共用原流程。
  内容类型按实际内容扩展联动、外观、活动、赛事、教学、主题曲和短视频；保留其它游戏原范围。
- 评测回填从 2026-07-02 起 2,992 条，覆盖首个补丁完整窗口；支持与鸣潮、绝区零同阶段比较。
  SteamDB 日均缺口不填，SteamCharts 月度仅在原总览作为独立参考；构建号镜像缺少 public branch，失败如实记录。
- 真实替换前保留 SQLite 备份；旧 v2 鸣潮 3.7 版本对照失败在未改动的 5c772cc 中亦可复现。

- **执行 SQL 脚本不能用 `executescript()`。** 它会先提交当前事务，迁移失败时就回滚不了。
  要逐条执行语句，并用 `sqlite3.complete_statement` 切分。
- **"测试一次就全过"要验证。** 故意放进去两个错误（出错时不回滚、为空时保留旧值），确认测试会变红，
  才能相信这些测试确实在检查规则。
- **给字段起名之前，先用数据检验它的含义。** 看到"日汇总里的 Players"就想当然地认作峰值，差一点把错误口径带进新系统。
- **新指标上线前先看一眼分布。** 一个字段如果所有行都是同一个值，做成指标只会得到一个看似有意义的 0%。
- **体积问题先测量再动手。** 逐表删除、看压缩后体积的变化，几分钟就能定位到重复存储，比猜测可靠。
- **Windows 脚本文件注意换行符和 BOM。** `register-tasks.ps1` 是 UTF-8 BOM + CRLF，按 LF 换行符匹配的替换会静默失败；改完要让 PowerShell 解析一遍确认没有语法错误。
- **YAML 解析是隐藏的性能瓶颈。** 1.5 万行的登记表用纯 Python 解析，测试 40 秒；换成 C 解析器并按修改时间缓存后 11 秒。
- **截图要真的看。** 图表不报错不等于画出来了：同龄对比图第一次截图里只有图例没有线。
- **示例内容也要被测试覆盖。** 默认示例 SQL、预设查询是用户最先点的东西，也最容易漏测；
  预设改成按当前数据生成，不写死游戏和版本号。
- **安全边界放在最底层。** 用文字规则判断"这条 SQL 是否只读"总有漏洞；页面既然从不写库，就让数据库本身只读。
- **"加起来"之前先问集合是否固定。** 累计值跨视频相加、比率跨游戏堆叠，SQL 都能算，但结果没有意义；这类规则要写进指标目录，由生成器强制。
- **端到端测试要等页面真正重绘。** 网址先变、页面后画，立即读值会偶尔读到旧值；这个测试之前"通过"只是运气。
- **动手前先盘点现有功能**（后台对照清单），结果发现了 4 种中位数算法、同一列数字有两种含义等问题，
  设计阶段就统一掉，而不是等迁移时才撞上。
