# Spike：SQLite + 浏览器 SQL 可行性验证（2026-09-29）

只读 v2 数据目录（`../game-ops-radar`），生成 `spike/out/gamepulse.sqlite`，
验证 v3「采集写 SQLite → 发布 .sqlite → 浏览器用 SQL 查询」方案。不改动 v2 看板。

```powershell
python spike/build_db.py                 # 导入，打印体积与行数
cd spike; npm install; node bench.cjs     # 浏览器基准（需先在仓库根目录 npm ci）
```

GitHub Pages 不压缩二进制文件，所以发布 `.sqlite.gz`，浏览器用原生 `DecompressionStream` 解压。

## 结论与对 v3 设计的影响

1. 方案可行：数据量下浏览器端可以现场做任意切片，交互级查询基本在 100 ms 内。
2. 慢的两类查询来自「评测 → 版本」的区间连接。构建时把 `version_id`、`day_index`
   直接写进评测表（Python 实测三维切片 99→51 ms），中位数再加
   `(game_id, version_id, playtime_at_review)` 索引（215→103 ms）。版本表极小、每次发布重建，物化没有一致性代价。
3. 首屏在慢网下 3 秒左右：固定看板页的首屏可以先读一份很小的预聚合 JSON，
   数据库在后台加载；自助探索页等数据库就绪。
4. 体积随评测线性增长（约 60 B/条压缩后 14 B/条）；按年增约 10 万条估算，
   几年内都在几 MB 级别，暂不需要分库。
